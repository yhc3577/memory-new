# 记忆系统对比研究：mem0 / dsh / TDB / Co-Engram

> 本文档对比当前项目已 clone 的四个记忆/上下文系统的设计取向,并据此推导一个记忆插件应该具备的能力。
>
> 调研基于源码路径:`mem0/`、`dsh/deepseek-harness/`、`tdb/TencentDB-Agent-Memory/`、`co-engram/Co-Engram/`。

---

## 0. 系统定位速览

| 系统 | 形态 | 核心抽象 | 数据来源形态 |
|---|---|---|---|
| **mem0** | 云优先的 LLM 记忆 SDK(OSS + Platform) | 单一平铺的"记忆条目"集合,按 `user_id / agent_id / run_id` 切片 | 向量库 + 隐式 `_entities` 旁路表 + 本地 SQLite 历史库 |
| **dsh** (DeepSeek Harness) | Agent 运行时框架 | 会话日志 + 多层 `PromptLayer` 注册表 + 触发式快照 | 本地 JSONL/SQLite 会话日志 + `storageDomain` 跨会话 K-V |
| **TDB** (TencentDB Agent Memory) | 企业级 Agent 记忆服务平台 | 4 类资产(skill/llm_wiki/code_graph/chat_memory) × `chat_memory` 内部 L0–L3 四层 | TCVDB 向量库(每个逻辑表一个 collection)+ COS / 本地 Blob 存 L2/L3 文件 |
| **Co-Engram** | 团队记忆 / git-native 知识库 | 4 条正交轴(kind / status / freshness / visibility)× 5 个披露层 | 磁盘 Markdown + YAML frontmatter + 派生 SQLite 索引 + git |

四者形态横跨三个范式:

- **平铺单库 + 多维度切片**(mem0)
- **运行时事件日志 + 即席上下文注入**(dsh)
- **多模态资产平台 + 显式蒸馏管线**(TDB)
- **认知神经科学隐喻 + git 原生协作**(Co-Engram)

## 1. 记忆分层与分类

### 1.1 mem0:扁平条目 + 正交维度

- 一类 `MemoryItem`,5 字段:`id / memory / hash / metadata / score`。
- 内容类型枚举只有 `SEMANTIC / EPISODIC / PROCEDURAL`,但代码里只有 `PROCEDURAL` 走了分支。
- 真正的"分类"是**身份键三元组**:`user_id / agent_id / run_id`,至少要填一个。`actor_id` 只做消息级归属,不参与切片。
- 每个主 collection 旁路一对 `_entities` collection,做实体链接,但不暴露 API。

> 实质上是"扁平池 + 多维过滤",没有显式的层级结构。

### 1.2 dsh:六层 prompt 切片,每层有 source discriminant

dsh 把"记忆"全部拆成会话日志上的 `user/message` 事件,通过 `source` 字段区分来源,组装时按 `PromptLayer` 的 `order` 排序:

| 层级 | 来源 discriminant | 形态 | 生命周期 |
|---|---|---|---|
| 1. Harness 身份/部署 persona | `plugin: @deepseek-ai/dsh-system-prompt` | section | 进程级 |
| 2. 工具指南(`context:file-reference` 等) | section name | section | 进程级 |
| 3. 运行时上下文(time/tmux/skill-catalog/session-reference) | `plugin: <name>`, `form: snapshot/catalog/recall` | 持久 user/message | 步级 / 变更驱动 |
| 4. 工作区指令(AGENTS.md / CLAUDE.md) | `agent-instructions`, `form: instructions` | 持久 user/message | 全 session,mtime 触发 |
| 5. 技能目录 + 技能体(`/name` 手势) | `skill-catalog` / `skill-invocation` | 持久 user/message | digest 变化 / 手势触发 |
| 6. 工具结果 + 用户提示 | `tool/result` / `user` | session 日志 | 单 turn |

读路径单点:`ReactLoopAgent.step()` → `assemble()` + `deriveMessages()` + `agent/pre-step` 钩子瀑布。每一轮都全量重算,不裁剪。

### 1.3 TDB:四类资产 × `chat_memory` 内 L0–L3 四层

**资产类型枚举**(全平台唯一):

```ts
// MemoryCore/src/metadata/types.ts:24
export type AssetType = "skill" | "llm_wiki" | "code_graph" | "chat_memory";
```

资产 ID 前缀按类型分配,前端按类型分别路由(wiki/code_graph 进 MemoryKnowledge,chat_memory 进 MemoryPanel,skill 走单独 store)。

**`chat_memory` 内部的四层蒸馏**:

| 层 | 内容 | 写入触发 | 存储 |
|---|---|---|---|
| **L0** 原始消息 | user/assistant turn 原始流 | 实时 append,按日期分片 JSONL | SQLite `l0_conversations` / TCVDB `l0_conversations` collection |
| **L1** 原子记忆 | LLM 抽取的事实/知识条目,带 priority、scene_name、owner triplet | 每 N 条对话或空闲 60s 触发 | SQLite `l1_records` / TCVDB `l1_memories` |
| **L2** 场景块 | 按主题聚合的 L1 摘要,带 `heat` 字段 | L1 完成后 90s 起,最小间隔 15 分钟,最大 1 小时 | 文件系统 / COS `.mmd` 文件 |
| **L3** Persona | agent 的"自我模型" | 5 条件触发(显式请求/冷启动/恢复/首个 scene/阈值) | 文件系统 / COS `persona.md` |

**`skill` 不进 L0–L3**,自己一套版本化存储(`is_head`/`version`/`manifest`),`wiki` 和 `code_graph` 走 MemoryKnowledge 服务的 wiki page graph。

### 1.4 Co-Engram:四条正交轴 × 五个披露层

四条独立维度,每个 engram 都独立标注:

```ts
// packages/core/src/types/engram.ts
EngramKind:    "observation" | "fact" | "pattern" | "procedure" | "hypothesis"
EngramStatus:  "draft" | "active" | "frozen" | "forgotten"
EngramFreshness: "fresh" | "aging" | "stale" | "forgotten"   // 派生
EngramVisibility: "public" | "team" | "private" | "restricted"
VerificationStatus: "unverified" | "plausible" | "probable" | "verified" | "refuted"
```

- **Kind** 形成 evolution ladder:observation → fact → pattern → procedure → hypothesis,可由 evidence 数量自动升级。
- **Status** 是生命周期:frozen = 完全冻结(不衰退、不强化、不检索),forgotten = 移出索引但 git 仍保留。
- **Freshness** 是派生量,纯函数 `(lastEffectiveAt, importance, kind)`。
- **Visibility** 是访问控制 ACL(不是 tier)。
- 另有一个**披露层(DisclosureTier)**决定返回的粒度:catalog → digest → content → meta → synapses。`Engram` 接口本身被拆成 `EngramCatalogEntry` / `EngramDigest` / 完整 `Engram` 三种返回形状。

### 1.5 对比表

| 维度 | mem0 | dsh | TDB | Co-Engram |
|---|---|---|---|---|
| 顶层"记忆种类" | 单一 MemoryItem | 6 个 source discriminant | 4 个 asset_type | 5 个 EngramKind |
| 是否有时间分层(短/长) | ❌ 无 | ❌ 无 | ✅ chat_memory L0/L1/L2/L3 | ❌ 无(走 status) |
| 是否有用户/Agent 切片 | ✅ user/agent/run 三元组 | ⚠️ 仅 SessionId | ✅ team/agent/session_key/task_id | ⚠️ visibility 字段,无显式 team 字段 |
| 分类粒度 | 粗(枚举仅分支 PROCEDURAL) | 中(按 prompt 层切片) | 粗(资产级) + 细(L0–L3) | 细(四轴 + 披露层) |
| 是否支持枚举之外的自定义 | 通过 `metadata` 自由扩展 | 通过 source discriminant 扩展 | `memory_type` 字段预留 | `kinds` 多标签 + `contextTags` |

**关键观察**:四家对"分层"的认知完全不同。mem0/dsh 不分时间层,靠 metadata/source discriminant 做正交区分;TDB 显式建模 L0–L3 的蒸馏管线;Co-Engram 用四轴 + 多披露层模拟"细节渐显"。一个成熟插件需要**至少支持两层时间维度**(短/长) + **多维度正交分类**(语义、作用域、生命周期、可信度)。

## 2. 记忆存取

### 2.1 mem0:30 种向量库适配 + 9 步混合检索

**存储后端**:`VectorStoreBase` 抽象 + 30 个 provider(qdrant / chroma / pgvector / pinecone / mongodb / milvus / elasticsearch / opensearch / faiss / supabase / weaviate / langchain / s3_vectors / turbopuffer / azure_* / redis / valkey / oracle / databricks / vertex_ai / baidu / cassandra / neptune / upstash / elasticsearch / langchain …)。旁路 SQLite `~/.mem0/history.db` 存变更历史与最近 10 条消息。

**API 表层**:`Memory.add / search / get_all / update / delete / delete_all / history()`。`add` 走 7 阶段批处理:上下文收集 → 已存记忆检索 → LLM 抽取 → 批量 embed → hash 去重 → 批量插入 → 历史 + 实体链接。

**检索管线**(9 步):

```
query → 词形还原 → 实体抽取 → embed
     → 语义检索(internal_limit = max(top_k*4, 60))
     → 关键词检索(若 vector store 支持 BM25)
     → sigmoid 归一化 BM25 → bm25_scores
     → 实体加权 → entity_boosts
     → 过滤过期 → score_and_rank(combined = (semantic + bm25 + 0.5·entity) / max_possible)
     → 可选 reranker(cohere / huggingface / llm / st / zero_entropy 5 种)
```

**元数据过滤 DSL**:`eq / ne / gt / gte / lt / lte / in / nin / contains / icontains / 通配符 */ AND / OR / NOT`,直接转译到向量库原生表达式。

### 2.2 dsh:读取路径全量重算,写路径单点序列化

**写路径**:

- 唯一提交口:`Session.append()`(`packages/core/session/src/index.ts:604-700`)→ 触发 `session/event` 总线 → `PersistenceCoordinator` 串行化每个 sessionId(`coordinator.ts:1010-1090`,Promise chain)→ JSONL(默认 zstd)或 SQLite 后端 → `SessionProjectionCache` 写后批(每 N 事件 / 间隔 ms)。
- 持久事件白名单:`turn/start|end`、`step/start|end`、`user/message`、`assistant/chunk`、`assistant/message`、`tool/call`、`tool/result`、`request/header`、`request/context`、`session/end-seed`、`compaction/*`、`todo/write`。
- 强制 flush 点:`agent/pre-step`、`tools/execute`、`llm/stream`,保证下一轮调用前日志已落盘。
- 跨会话长存:`storageDomain.open(defineDomain(...))` 提供类型化 `Domain<S>`,所有插件可声明自己的长存 schema,写入触发 `domain/changed` 事件。

**读路径**(单点):

```
ReactLoopAgent.step()
  ├─ systemPrompt.assemble()         // 重算所有 section
  ├─ renderContextSections()         // 转 content blocks
  ├─ runtimeContext.project()        // 决定是否新增 snapshot 消息
  ├─ agent/pre-step waterfall        // 钩入 session-reference / time-context / skill catalog…
  └─ session.deriveMessages()        // 全量返回 surface.nodes,无裁剪
```

**真正"召回"的只有 `session-reference`**:用户写 `@[label](dsh-session:...)` → 拉一次对方 session 的 surface 快照 → 加进当前会话,有 3 条 / 65 KB / 50 候选的上限,渲染时还明示模型"这是不可信快照"。

### 2.3 TDB:两套存储抽象 + 蒸馏管线 + 双策略检索

**两套抽象**:
- `IMemoryStore`:L0/L1/profile/knowledge 向量存储。SQLite(vec0 + FTS5,默认)与 TCVDB(腾讯云,生产)两种实现,TCVDB 用一个 collection 一个逻辑表。
- `IStorageBackend`:L2/L3 markdown 文件。`LocalStorageBackend` 与 `CosStorageBackend`(生产),append 是原子操作(COS `?append&position=N` 协议,带 409 重试)。

**写入侧管线**(`pipeline-manager.ts`):

```
对话流 → L0 实时 append → 阈值触发 L1 → L1 完成后 90s 触发 L2 → L2 完成后条件触发 L3
         5 行为          5 条/批 或 60s 空闲  间隔 15 分钟以上           5 个触发条件
```

每层独立 runner,失败不阻塞上层;`auto-capture` / `auto-recall` 钩子接到 L0。

**读取侧**:

- L1/L0 混合搜索:RRF(`K=60`)合并 dense + sparse,`strategy: "hybrid" | "embedding" | "fts" | "none"`。
- Wiki 多跳 BFS,每跳乘以 `decay ∈ [0,1]`,`maxNodes=200`。
- 对话搜索:top_k=10 L1 召回 + FTS。

**API**:HTTP 网关 `/v3/conversation/{add,query}`、`/v3/atomic/query`、`/wiki/{get,search,graph}`;Panel 层面对前端只暴露 `metaKernel.invoke("asset/list", {team_id, asset_type, ...})`。

### 2.4 Co-Engram:git-native + SQLite 派生 + FTS5

**真相源**:磁盘 Markdown 文件 + YAML frontmatter。`packages/core/src/storage/engram-store.ts:740-747` 用 `mkdirSync + writeFileSync`,无 vector DB。

**派生索引**:`node:sqlite`,WAL 模式,主表 `engrams` + `engram_domains` + `synapses` + FTS5 trigram 虚表。

**检索接口**:

```ts
interface SearchEngine {
  search(query, filter?, limit?): SimpleSearchResult[];
  build(lines: readonly DigestLine[]): void;
}
```

两种实现:内存版 (`SearchOrchestrator`) 与 SQLite 版 (`SqliteSearchOrchestrator`,默认)。`CO_ENGRAM_SEARCH_ENGINE=memory` 可切到内存版(开发用)。

**5 因子打分**(`retrieval/scoring.ts:290-323`):

```
score = 0.50·relevance + 0.15·recency + 0.25·effectiveImportance + 0.05·strength + 0.05·hotness
```

| 因子 | 来源 | 计算 |
|---|---|---|
| relevance | FTS (trigram) | [0,1] 归一化 |
| recency | Ebbinghaus | `0.5^(ageDays / halflife)` |
| effectiveImportance | 静态 importance × 真值约束 | `importance × (0.3 + 0.7·truthFactor)` |
| strength | 用户反馈 | `clamp01(reinforcementScore)` |
| hotness | 检索计数(纯派生) | `sigmoid(ln(1+count)) · exp(-ln2·ageDays/7天)` |

**写入时连带触发**:`observability/team-event-store` 把团队同步事件写到 `events/<YYYY-MM-DD>/<origin>.jsonl`(每机器单写者,git merge 零冲突);审计日志只写本地 `.co-engram/audit.jsonl`;SQLite 是 write-through。

**团队摄入**:git 跟踪的 `.md` → `adoptOrPromoteEngramAt` 直接纳管;非 git 跟踪的 → 走 `proposalEngine`,必须 `engram_accept_proposal` 才晋升。

### 2.5 对比表

| 维度 | mem0 | dsh | TDB | Co-Engram |
|---|---|---|---|---|
| 主存储 | 向量库(30 种) | 会话日志(JSONL/SQLite) | 向量库 + Blob 文件 | Markdown 文件 + 派生 SQLite |
| 检索模型 | dense + sparse + entity-boost | 全量派生 + 显式引用召回 | dense + sparse + RRF + 多跳 decay | FTS5 + 多因子加权 |
| 写入触发 | 同步 API | 事件总线 + 写后批 | 阈值/空闲时间触发的多阶段蒸馏 | 同步 API + 事件追加 + git commit |
| 跨会话 | 仅通过共享 `user_id` | `session-reference` URI 显式拉取 | `imported_agent_ids`(≤ 2) | git push/pull + 写入分流 |
| 元数据 DSL | 完整过滤语法 | source discriminant | TCVDB 原生 filter | metadata 自由字段 + visibility ACL |

**关键观察**:
- **存储选型上,mem0/TDB 偏中心化服务,Co-Engram 偏 git 原生协作,dsh 偏本地事件日志**。
- **检索管线复杂度递增**:mem0 < dsh < TDB < Co-Engram。
- **dsh 是唯一一个"读 = 全量重算"的系统**——它假设 session log 不长,内存里有完整 surface;Co-Engram 走磁盘 + SQLite 也是为了支持巨大文件库的检索。
- **TDB 唯一实现真正的自动蒸馏管线**(L0 → L1 → L2 → L3),其它三家都是"写即所得"或"写即归档"。

## 3. 记忆衰退机制

### 3.1 mem0:几乎无衰退

- 唯一的生命周期机制是 `expiration_date`:写入时 `add(..., expiration_date=...)`,读取时 `_payload_is_expired(payload)` 在结果集里过滤,**不会自动清理**。
- OSS 显式拒绝 `decay` 参数(`memory/main.py:461-471`),只允许 Platform 上 `project.update(decay=True)`。
- Platform `decay` 文档是"检索时给最近使用的记忆加权",**不是删除机制**。
- 没有重要性分数、没有访问频率统计、没有定时清理任务。
- 内部 telemetry `detect_decay_usage_from_delete` 统计用户主动 `delete` 的次数(5 次 / 7 天触发 nudge),只是营销。

### 3.2 dsh:Token 压力触发的压缩

唯一机制是 `compaction-basic` + `compaction-tool-result-pruner`,**显式、按需、token 驱动**。

**触发条件**:

| 来源 | 行为 |
|---|---|
| `agent/pre-step` 每步 | 测 token,达到 `0.8 × contextWindow` → 压 |
| `agent/request-error` + `CONTEXT_WINDOW_EXCEEDED_CODE` | 直接压,返回 `{kind: 'retry'}`,上限 `maxOverflowRetries=1` |
| `/compact` 命令 | `compactNow()`,必须 idle |

**压缩算法**:

1. 从尾部回溯到累计 ≥ `retainTokens`(默认 `0.16 × contextWindow`)。
2. 回退到最近的 tool-call/result 对齐边界(绝不拆对)。
3. 重放前缀对话让 LLM 重生成 summary(KV cache 复用)。
4. 校验 framed summary 必须 net-save(`framedTokens < shadowedTokens`),否则抛错。
5. 提交为新 user/message,`surfaceOp: {op: 'replace', start, end}`,原始事件留在日志里(append-only),通过 `shadowedSeqs` 引用。

**工具结果修剪**(model-free):`thresholdChars=8192 / headChars=4096 / tailChars=1024`,超长在中间插入 `[... tool result middle pruned ...]` 标记,只发 `compaction/prune` shadow-price 事件,不独立运行。

**没有的机制**:TTL、过期、LRU、age 淘汰、定期清理。

### 3.3 TDB:时间淘汰 + 安全护栏 + 检索时图衰减

**L0/L1 保留期**(`memory-cleaner.ts`):每天本地时间固定时刻跑一次,按"自然日"切(`keepStart = today - (retentionDays - 1) 天`)。删除前先校验比例:

```ts
// tcvdb.ts:1185-1191
if (ratio > 0.8) {
  this.logger?.warn(`BLOCKED: would delete ${toDelete}/${total} (${(ratio*100).toFixed(1)}%) — exceeds 80% safety threshold`);
  return 0;
}
```

**最低保留**:`MIN_RETAIN_L0 = 50`,`MIN_RETAIN_L1 = 20`,低于阈值直接跳过删除。

**Wiki 多跳衰减**(`graph-search.ts`):

```ts
export interface GraphSearchOptions {
  hop: number; decay: number;    // 0..1, 每跳乘性
  minScore: number; maxNodes?: number;
}
// nbScore = cur.score * decay,掉到 minScore 丢弃;多路径取最高
```

**`SceneBlockMeta.heat`**:有字段,但**只读不衰减**,没有 `applyHeatDecay` 之类的函数。看上去是为后续预留的接口。

**没有的机制**:per-record 重要性评分接入保留、Ebbinghaus 遗忘曲线、LLM 判定重要性。

### 3.4 Co-Engram:完整的神经科学衰退栈

这是四家里做得最深的,有 **4 套协同的衰退/强化机制**:

**(1) Freshness 派生**(实时,纯函数)

```ts
// lifecycle/freshness.ts:63-77
if (ageDays <= halfLife) return "fresh";
if (ageDays <= halfLife * 2) return "aging";
if (ageDays <= halfLife * 4) return "stale";
return "forgotten";
```

半衰期由 importance 派生:

```ts
// importance/dynamics.ts:83-89
halflife = BASE(50) * (importance + 0.1)^1.5 * kindMultiplier(kind)
// 0.6 / 0.7 / 0.8 / 1.0 / 1.5 (observation / hypothesis / procedure / fact / pattern)
```

**(2) `applyDecayBatch` 批处理**(Deep Dreaming 阶段)

```ts
// dreaming/decay.ts
freshness=forgotten                       → forget
freshness=stale && importance < 0.2       → forget
freshness=stale && importance ≥ 0.2       → archive (frozen)
freshness=aging/fresh                     → no-op
```

**(3) LTP / LTD 事件驱动重要性变更**

```ts
// importance/dynamics.ts:24-25
const LTP_GAIN     = 0.1;     // 强化时 importance 增量
const FAILURE_LOSS = 0.1;     // 失败时 importance 减量
```

`reinforce` 工具路径走 LTP,`failure` 路径走 LTD。**显式声明删除了"基于时间的 importance 衰减"**(`importance/dynamics.ts:10-15` 注释:"时间不直接降低突触强度")。

**(4) Hotness 派生(零债)**

```ts
// retrieval/scoring.ts:233-252
hotness = sigmoid(ln(1 + retrievalCount)) · exp(-ln2 · ageDays / 7days)
```

无需后台任务,读时现算。

**(5) REM / Deep Dreaming 跨条目整合**(`dreaming/`):`rem.ts`(升阶 observation → fact → pattern → procedure)、`deep.ts`(跨 cluster 抽象)、`light.ts`(轻量后台重组)、`trash.ts`(清扫 forgotten)。

### 3.5 对比表

| 机制 | mem0 | dsh | TDB | Co-Engram |
|---|---|---|---|---|
| 时间过期 | `expiration_date`(过滤不删) | ❌ | ✅ retentionDays + 80% 安全护栏 | ✅ Ebbinghaus(由 importance 派生) |
| 重要性评分 | ❌ | ❌(只按 token) | ❌(priority 仅排序) | ✅ LTP/LTD 持续演化 |
| 访问频率加权 | ❌ | ❌ | ❌ | ✅ hotness |
| 检索时衰减 | ❌(只在 Platform 有 decay flag) | ❌ | ✅ graph 多跳 `decay` 参数 | ✅ recency = `0.5^(ageDays/halflife)` |
| 状态机(draft/active/frozen/forgotten) | ❌ | ❌(仅 compacted/original) | ❌(L0/L1/L2/L3 是层级非状态) | ✅ 显式状态机 |
| 跨条目整合/抽象 | ❌ | ❌(仅 summary) | ❌ | ✅ REM / Deep Dreaming |
| 自动后台清扫 | ❌ | ❌ | ✅ 每日定时 | ✅ applyDecayBatch(显式触发) |

**关键观察**:
- **mem0 是"无衰退"哲学**:交给用户用 `expiration_date` 显式管,或上 Platform 让 SaaS 加分。
- **dsh 是"token 驱动"哲学**:不关心语义重要性,只关心能不能塞进上下文窗口。
- **TDB 是"运维安全"哲学**:时间一刀切,加 80% 护栏防止误删。
- **Co-Engram 是"神经科学"哲学**:从 importance 派生半衰期,事件驱动强化,REM 阶段跨条目抽象。
- 一个插件如果要兼顾,需要至少 **5 个可独立开关**:TTL、importance-driven 半衰期、access-count 加权、显式状态机(冻结/遗忘)、跨条目整合触发器。

## 4. 团队记忆

### 4.1 mem0:无团队记忆原语

- OSS 和 Platform 都**没有 team 字段**。
- "Org / Project" 仅是 Platform 账号级隔离,通过 API key 解析,不参与 memory 切片。
- `app_id`(Platform 唯一)是第 4 个独立 scope,作用是隔离,不共享。
- 跨用户共享的唯一办法:**大家都用同一个 `user_id`**。
- 文档里提到过"CrewAI shared memory",但那是应用层(CrewAI agents 共用一个 user_id),不是 mem0 的原语。

### 4.2 dsh:没有"团队"抽象,只有"进程"和"实验性 Team"

- 三层身份:`SessionId`(会话)、`<dshHome>`(部署用户)、`TeamId === SessionId`(experimental `agent-team`)。
- 实验性 `agent-team` 的限制(README):
  - **一个进程 + 一个共享 checkout**——成员共享 cwd,不支持 worktree / 远程成员 / merge / fs lock。
  - **Mailbox 不跨进程 exactly-once**——不支持多进程共管一个 team。
  - **平面不可变 roster**——只有 Lead 能创建直接 teammates,不支持嵌套 / 重命名 / 删除 / name reuse。
- 跨 session 读的唯一原语:`session-reference`,**用户写 URI 才拉取**,且最多 3 条 / 65 KB。
- 其它"共享"都是文件系统语义:preset 目录、`<dshHome>/AGENTS.md`、profile bundle。

### 4.3 TDB:显式的"借入/共享"团队模型

数据模型(`MemoryPanel/src/panel/domain/chat-memory-governance.ts`):

```ts
export const MAX_IMPORTED_AGENTS = 2;

export interface ChatMemoryAgentRel {
  memory_shared_with_team: boolean;      // 本期 UI 锁定 true,只要有就全局展示
  imported_agent_ids: string[];          // 借入的 agent_id(≤2, 必须同 team, 不含自己, 去重)
}
```

- 当前存储位置是 `Agent.metadata_json["chat_memory"]` namespace,**没有真正的 schema 列**(代码注释明确写:演示阶段临时方案)。
- 校验函数 `validateImportedAgents(selfId, ids, teamAgents)` 共享前后端:数组性、≤ 2、字符串、非自、必须同 team、去重。
- 两个动作语义分离:
  - **share out**:`patch-scope` 把 `visibility` 切成 `team` 或 `private`(owner-only)。
  - **import in**:`allocate` / `batch-set-fixed` 把另一个 agent 的 chat_memory 绑给自己(走 `meta_agent_fixed_assets` 表),受 `MAX_IMPORTED_AGENTS=2` 限制。
- 权限模型不信任 client:每个请求通过 `resolveCallerUserId(deps, ctx)` → `auth/verify` → 拿 `agent/owner_user_id` 比对。
- 跨 agent 注入:L0 写入仍用 caller 的 sessionId(对话归属不变),但 L1 检索和 L2/L3 读取用借入 agent 的 owner triplet(`fromAgentId` 字段标记来源)。

### 4.4 Co-Engram:git 原生 + 4 层可见性 + 3 阶段冲突仲裁

**存储拓扑**(`storage/git.ts:604-627`):

```
.co-engram/        # 不入库(SQLite 索引 + 审计日志 + 行为缓存,可重建)
private/           # 不入库(visibility=private 的私人 engram)
events/<date>/     # 入库(跨机器团队活动流,按 origin 写者分片,git merge 零冲突)
**/*.md            # 入库(public/team/restricted engram)
synapses/**        # 入库(突触边)
.obsidian/         # 不入库(用户态)
```

**可见性闸门**(`storage/visibility-gate.ts`):

```ts
// 单向闸门:禁止任何 → private 的转换
// 允许:public ↔ team ↔ restricted (可逆)
// 允许:private → 任意 (单向开放,实际很少用)
// 禁止:任何非-private → private
```

理由:`private` 路径进 `.gitignore`,非-private 切到 `private` 会让其他成员 git 工作树里该记忆消失(隐性删除)。

**3 阶段冲突仲裁**(`contradiction/resolver.ts`):

```
阶段 1 — LLM 自动裁决(confidence ≥ 0.8) → 执行 verdict(keep_new/keep_old/merge)
阶段 2 — 升级归属人(confidence < 0.8 或 verdict=archive) → 标 escalated + expiresAt
阶段 3 — 超时降级(processExpiredContradictions)
```

**verdict 副作用**:

- `keep_new`:旧方 `verificationStatus = 'refuted'`
- `keep_old`:新方 `verificationStatus = 'refuted'`
- `merge`:合并到旧方,删 contradicts synapse
- `archive`:仅升级到人,不自动执行

**多视角保留**(`perspectives/multi-view.ts`):**矛盾 engram 并存,都可检索,不强制消除**;检索时主动展示 contradicts 关系,标注 `resolutionState`,`perspective` 字段记录视角 ID。这是抗"单视角确认偏误"的明确设计取舍。

**git merge driver**(`merge/driver-main.ts`):`engram` / `synapse` / 非 engram 三类分别路由;`engram` 用两阶段 merge:Layer A 机械规则 + Layer B LLM 兜底仲裁。

**提案管线**(非 git 来源,如 Claude Code auto-memory):`AutoMemorySyncEngine.syncMemory` → `proposalEngine.proposeAutoMemory` → 必须 `engram_accept_proposal` 才晋升为 engram。git 跟踪 vs 非跟踪是信任分界。

**技能分发**(`skill/skill-distributor.ts`):团队仓库 `team-memory/skills/` 中的 skill 复制到 host 技能目录(`~/.claude/skills/`、`~/.openclaw/skills/`);D11 规则——目标已有同名 skill 不覆盖(本地优先)。

**跨主体涌现**(`generative/`):`cross-pollinate`(找共享模式)、`gap-detector`(找缺失连接)、`hypothesis`(从缺口生成可验证 engram)。

### 4.5 对比表

| 维度 | mem0 | dsh | TDB | Co-Engram |
|---|---|---|---|---|
| 团队作为一等公民 | ❌ | ❌(实验性,单进程) | ⚠️(资产级 share + agent 级 import) | ✅(默认就是团队) |
| 共享模型 | 共用 user_id | 文件系统 / URI 拉取 | `memory_shared_with_team` + `imported_agent_ids` | visibility ACL + git push |
| 冲突解决 | 无 | 无 | 无 | 3 阶段 LLM 仲裁 + 多视角保留 |
| 跨 agent 注入身份 | 无 | 无 | `fromAgentId` | perspective + resolutionState |
| 信任分界 | 无 | 无 | owner_user_id 校验 | git-tracked vs proposal 管线 |
| 跨机器同步 | n/a | n/a(单进程) | 后端服务 | git + events/ JSONL 写者分片 |
| 多视角/冲突并存 | n/a | n/a | n/a | ✅ 显式支持 |

**关键观察**:
- mem0 完全跳过团队维度,把"团队"推到账号和 ID 选择层。
- dsh 把团队当作"单进程多 session"的实验性功能,**不支持多机器**。
- TDB 是**唯一有 borrow/import 上限**(MAX_IMPORTED_AGENTS=2)+ 显式 share/import 动作分离的,但仍依赖一个中心服务。
- Co-Engram 是**唯一把团队作为默认存储形态**的——git 原生协作 + 冲突仲裁 + 多视角保留。
- 一个插件如果要支持团队记忆,需要至少 **5 个能力**:scope 字段(visibility/share flag)、borrow/import 限额、跨身份读时标签、冲突仲裁流程、信任分界(git-tracked vs proposal-like)。

## 5. 总结:一个记忆插件应该具备的能力

综合四家设计,**一个成熟、可演进的记忆插件**应至少具备以下能力集。我把它们分成 6 大类:

### 5.1 分类与建模能力

1. **多维正交分类,而不是单层枚举**
   - 至少 4 条独立轴:语义类(fact/observation/pattern/...)、生命周期(draft/active/frozen/forgotten)、可信度(unverified/verified/refuted)、作用域(public/team/private/restricted)。
   - 任意 engram 可同时属于多条轴(多标签),不要限制成单分类。
   - mem0 的单层 `MemoryType` 枚举(只分支 PROCEDURAL)是反面案例。

2. **多粒度披露层**(progressive disclosure)
   - 同一条记忆至少返回 3 个粒度:catalog(标题+ID+类)→ digest(+ 摘要+重要性+新鲜度)→ content(+ 正文)→ meta(+ 全 frontmatter)→ synapses(+ 关联图)。
   - Co-Engram 的 `DisclosureTier` 是参考实现。

3. **预留层级时间维度**
   - 即便当前只做平铺,也应在 schema 上预留短/长两条 pipeline(如 TDB 的 L0/L1/L2/L3),否则后期很难补。

### 5.2 存取能力

4. **混合检索管线**(dense + sparse + entity/relation boost)
   - 至少实现:语义 + BM25(关键词)+ 实体/突触加权,加性合并,可选 reranker。
   - 检索时**over-fetch**(mem0: `max(top_k*4, 60)`),打分后再截断。
   - 支持元数据 DSL(`eq / ne / gt / in / contains / AND / OR`),不要只支持 `metadata.key=value` 字符串匹配。

5. **插件可替换的存储后端**
   - 向量库、blob 存储、KV/SQLite 各自有接口(参考 mem0 30 种向量适配器,TDB 的 `IMemoryStore` + `IStorageBackend` 双抽象)。
   - 同一接口至少两种实现(本地 + 生产),便于开发与部署切换。

6. **跨会话显式召回原语**
   - dsh 的 `session-reference` 是最简参考:用户显式 URI 拉取,有上限(条数 / 字节 / 候选数),渲染时标注"不可信快照"。
   - 不能让 agent 静默跨会话读,必须有"显式提及 + 限额 + 风险标注"三件套。

7. **可序列化的单写者写路径**
   - 写入是单 commit gate(参考 dsh `Session.append()`),按 ID 串行化(`Promise chain` per sessionId),写后批(批大小 + 间隔),强制 flush 点(`pre-step` / `tools/execute` / `llm/stream`)。
   - 事件 append-only,不要支持"删除"原语,只支持"打 shadow 标记"(参考 dsh 的 `shadowedSeqs`)。

### 5.3 衰退能力

8. **多种衰退机制并存,各自可独立开关**

   | 机制 | 何时启用 | 实现要点 |
   |---|---|---|
   | **TTL / 时间淘汰** | 运维侧,按天定时 | 必须有 80% 安全护栏(单次不能删超过总量 80%),最低保留数(参考 TDB `MIN_RETAIN_L0/L1`) |
   | **重要性驱动半衰期** | 召回侧 | 半衰期 = `BASE × (importance + 0.1)^α × kindMultiplier`(参考 Co-Engram `dynamics.ts`) |
   | **访问频率加权** | 召回侧 | hotness = `sigmoid(ln(1+count)) · exp(-ln2·ageDays/7天)`,纯派生无需后台任务 |
   | **状态机** | 写入侧 | draft → active → frozen → forgotten 四态,frozen 完全冻结(不衰退/不强化/不检索) |
   | **检索时图衰减** | 多跳检索 | `nbScore = cur.score × decay`,`decay ∈ [0,1]` 必须服务端校验范围 |

9. **重要性是事件驱动而非时间驱动**
   - 不应该有"每天 importance -= 0.01"。
   - 应该有 `LTP` / `LTD` 两条显式路径,只有用户/系统显式 `reinforce` / `failure` 才改 importance(参考 Co-Engram 显式移除时间衰减的注释)。
   - 跨条目整合(REM/Deep Dreaming)是可选项,但若有,必须独立于常规读写路径,不阻塞响应。

10. **淘汰策略有上限保护**
    - 任何"批量淘汰"都必须有"单次最多删 80%"+"最低保留 N 条"两道闸(参考 TDB)。
    - 没有任何淘汰是"开箱即用"的,默认全部禁用,由配置显式开启。

### 5.4 团队能力

11. **visibility 字段 + 单向转换闸门**
    - visibility 至少 4 档:public / team / private / restricted。
    - **禁止任何 → private 的转换**(因为 private 路径不进共享存储,会变成"隐性删除")。
    - 允许 private → 任意 / public ↔ team ↔ restricted 互转。
    - Co-Engram 的 `visibility-gate.ts` 是参考实现。

12. **borrow/import 限额 + 共享/借入动作分离**
    - "我自己可见"(`patch-scope`)与"我看别人"(`allocate`/`import`)是两个动词,不能合并(参考 TDB 的 `ChatMemoryAgentRel`)。
    - 借入必须有上限(参考 `MAX_IMPORTED_AGENTS=2`),且校验函数必须前后端共享。

13. **跨身份读时标签**
    - 当 agent B 借用 agent A 的记忆时,每条 hit 必须带 `fromAgentId` 标签(参考 TDB `TdaiL1Hit.fromAgentId`)。
    - 否则审计、撤销、计费都没法做。

14. **冲突仲裁流程**
    - 至少 3 阶段:自动裁决(confidence 阈值)→ 升级归属人 → 超时降级(参考 Co-Engram `contradiction/resolver.ts`)。
    - verdict 必须有副作用定义:keep_new / keep_old / merge / archive。
    - 矛盾 engram **默认并存**(多视角保留),不要默认做"消除"——抗认知失调。

15. **信任分界**
    - 来源不同,信任级别不同。Co-Engram 的"git tracked = 直接纳管 / 非 git = proposal 必须 accept"是范式。
    - 至少要区分:本机直接写入、外部推送、第三方自动提取、应用层 API 提交——给每条入站记忆一个 `trustLevel`,影响默认 visibility 与是否走提案。

16. **跨机器同步的写者分片**
    - 任何"团队同步"原语,落地必须是写者分片 + append-only 文件(参考 Co-Engram `events/<date>/<origin>.jsonl`)。
    - 不要依赖集中式锁,git merge 零冲突是底线。

### 5.5 可观测性 / 演化能力

17. **演化 ladder**
    - 同一 engram 可从低层升到高层(`observation → fact → pattern`),由证据数量自动触发(参考 Co-Engram `evolution/`)。
    - 不要让 kind 是 frozen 的——记忆的价值会随时间显现。

18. **审计与回放**
    - 团队事件流必须可回放(append-only JSONL + git)。
    - 每条记忆的修改/强化/遗忘必须有 audit trail(`co-engram/audit.jsonl`)。
    - 不要只保留最终状态。

### 5.6 工程基线

19. **schema 版本化 + 软迁移**
    - 任何 metadata 字段都应有 `schemaVersion`,旧值不可读时走默认而不是抛错(参考 TDB `readChatMemoryRel` / `writeChatMemoryRel` 的 `try/catch` + 默认值)。

20. **分阶段管线 + 可重放**
    - 如果做蒸馏管线(L0/L1/L2/L3),每阶段必须独立、可重放、可观测;失败不阻塞上层。
    - 触发器(每 N 条 / 空闲 N 秒 / 显式请求)清晰可见、可配置、可单独关停。

21. **owner-only 权限持久化**
    - 本地 SQLite 必须 owner-only POSIX(`mode & 0o022 === 0`),参考 dsh `session-persistence-sqlite/src/store.ts:407-413`。

## 6. 四个系统选用建议

| 场景 | 推荐 | 理由 |
|---|---|---|
| 单 agent + 快速集成 + 多语言 SDK | mem0 | API 简洁、向量库适配最广 |
| 单 agent + 长 session + token 严格预算 | dsh | token 驱动压缩最成熟 |
| 企业多 agent + 多类资产 + 运维治理 | TDB | 资产/L0–L3 + owner 校验 + 借入限额最完整 |
| 团队协作 + git-native + 抗认知失调 | Co-Engram | 唯一把团队当一等公民、冲突仲裁、演化 |

如果需要**自研一个记忆插件**,起步最值得抄的是 **Co-Engram 的分类维度 + 衰退栈 + 单向 visibility 闸门**,以及 **TDB 的 borrow/import 限额 + owner-only 持久化 + 安全淘汰护栏**,加上 **dsh 的单 commit gate + 写后批 + 强制 flush 点**,最后用 **mem0 的混合检索管线 + 元数据 DSL** 做收口。
